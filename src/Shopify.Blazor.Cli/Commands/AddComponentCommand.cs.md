# AddComponentCommand.cs

`shopify-blazor add component <Name>` — writes a usage snippet for a wrapper the catalogue knows, or
prints it when there is nowhere to put it. It never invents a wrapper: an unknown name fails with the
closest known names, and a name that Shopify ships but the toolkit has not wrapped is reported as such.

`Shopify.Blazor.Cli.Commands` · the `add component` command · no base class

## Behaviour that is not in the member list

The order of decisions in `Run`, because several of them are only visible through it:

1. Exactly one positional argument, or `error: 'add component' takes one component name…` and exit 2.
2. The catalogue loads. A `CatalogueException` is printed as `error: <message>` and exits **5**
   (`InternalError`) — the CLI's own data is missing, not the developer's command line.
3. The root is `--project` resolved against `currentDirectory`, else `currentDirectory` itself.
4. `Find` — an unknown name goes to `ReportUnknown`.
5. The destination is resolved, and an existing file without `--force` stops the command with exit 3
   and a message naming the path and both ways out.
6. `--dry-run` prints what would happen and the snippet, then exits 0 without writing.
7. Otherwise the snippet is written (parent directories included), `Created <path> (<Wrapper> ->
   <element>)` is printed, and finally the parameter list as `Name:Type` pairs — the snippet itself is
   *not* echoed when it went to a file.

`ReportUnknown` reads `tools/polaris-elements.json` through `PolarisElementsReader` to decide between
two endings:

| Situation | Output | Exit code |
|---|---|---|
| The name is in the element spec | "Shopify ships the element — but the toolkit has no wrapper for it yet", plus `python3 tools/generate-component.py` | **0** |
| The name is nowhere | The catalogue's wrapper names, alphabetised, with a count | 2 |

## Gotchas

- **"No wrapper yet" is a successful run.** That branch returns `ExitCodes.Success`, so a script that
  checks `$?` sees success even though nothing was written. Decide whether a file appeared by looking
  for the file, not the exit code.
- **`--force` overwrites whatever is at the destination.** The check is existence only; nothing looks
  for a marker proving the file was generated by this command, so `--path SomePage.razor --force`
  replaces a real page.
- **A non-existent `--path` directory is created, not rejected**, because the write creates its
  parents. A typo therefore produces a new tree containing one `.razor` file, with no warning.
- **The snippet is prose, not a runnable example.** `ComponentUsageTemplate` emits the wrapper element
  plus Razor comments — the catalogue records a parameter's type but not a legal value for it, and a
  generated `Variant="…"` looks like working code while failing to compile.
- **`--path` resolves against the `--project` directory when one is given**, not against the shell's
  current directory. Passing both means two different bases for one relative path.
- `IFileSystem` is held for writes and for the element-spec read; `IEnvironment` is held but not used
  in `Run`, which takes `currentDirectory` as an argument instead.
